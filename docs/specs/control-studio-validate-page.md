# Control Studio — Validate page

User-directed UI specification, 13 September 2026.
Implementation and rendered acceptance are pending.

## Scope and authority

Validate is the third page of **Identify → Tune → Validate**. It checks the
tuned controller and provides **Apply** on the same page.

This document is the layout authority for Validate. The
[shared UI clarity contract](35-vscode-control-studio.md#shared-trust-uiux-contract--mandatory)
applies to every label, field, result and interaction.
[Specification 35](35-vscode-control-studio.md) and the
[complete workflow specification](control-studio-complete-workflow-specification.md)
own scenarios, requirements, runtime authorization and coherent application.
Reuse shared truST components and theme, consistently with
[Identify](control-studio-identify-page.md) and [Tune](control-studio-tune-page.md).

## Exact page contents

Show these elements, in this order:

1. **Identify / Tune / Validate** navigation, with Validate selected.
2. **Validate controller** button.
3. A compact results table: **Requirement / Measured / Limit / Result**.
4. The **measured response plot**.
5. **Apply** button; after confirmed application, the same position holds
   **Restore previous settings**.

Do not add other permanent controls, headings, descriptive paragraphs or
information panels to this page.

Use the [shared automatic flow](control-studio-complete-workflow-specification.md#three-page-automatic-flow)
for automatic continuation, autosave, reopening and runtime restart behavior.
This page does not duplicate Limits, Requirements or Channels editors.

## Validate controller

Tuning stops with the candidate for review. **Validate controller** explicitly
starts validation; neither Tune nor page navigation starts it automatically.

For a provisional identified model, first collect the independent live plant
recording here. Compare frozen-model predictions against its actual applied inputs
and measured outputs, preserving channels, operating point, delays and initial
conditions. Do not refit the model against validation data or compare it only
against measurements generated by that same model. Show model error and its limit
as mandatory rows in the existing results table. While this acquisition runs,
show the arriving live plant samples in the existing response plot.

Only a passing independent model check qualifies the model. Then Run the actual ST controller
against the configured simulated plant. Compare current and tuned settings
under the same required conditions, including declared setpoint/load events,
initial state and timing. Use the target, model, settings, channel mappings and
requirements already held by the workflow; do not repeat setup on this page.

Execute the applicable required scenarios automatically. Do not ask the user
to start each test separately. The primary PID journey must execute the real
**Control.PID**, not a handwritten substitute or a mathematical prediction
presented as executed ST. Other supported controllers use their existing
execution adapters.

Validation checks the proposed settings without applying them to the selected
running controller.

While validation runs, the button becomes **Abort**, with one short progress
message. If the operation fails, show one short, specific message in that area.
Keep any results that were obtained; missing checks must not appear as passed.

## Results and plot

The table shows the applicable requirements and their measured values, limits,
units and **Pass**, **Fail** or **Inconclusive** results. Show failed requirements
directly in their rows. Do not hide a failure in a details panel.

Settling time, overshoot and steady-state error in the layout below are
examples. The actual table must contain all required checks for the selected
controller and task. A required scenario that did not complete is Inconclusive.

The plot is labelled **Measured response**. Show the recorded current and tuned
controller responses with a small **Tuned / Current** legend and axes with
signal units and time. Use the actual execution recordings, not the predicted
curves from Tune. For multiple outputs, preserve the corresponding channels.

Before results exist, omit empty result rows and placeholder reports.

## Apply

**Apply** becomes available only when every mandatory requirement passes for
the current candidate. Changes to the model, selected controller, settings or
requirements invalidate the old result for application and require validation
again. Failed, incomplete or stale validation must not enable Apply.

Pressing **Apply** writes the exact validated settings directly to the actual
controller instance selected in Tune, using its declared parameter/state
mapping. A choice of PI or PID alone is not an instance selection and must not
authorize a write. For **Control.PID**, its adapter maps the tuned settings to
that instance's complete parameter record and required state initialization.
Use the existing [controller binding contract](control-studio-controller-bindings.md);
never infer the target from similarly named variables. The user must not have
to copy gains or edit ST manually to apply the result.

For an individual PID, **Apply** updates only the instance selected in Tune.
For an explicitly selected multichannel group, it updates exactly the mapped
members together through the supported coherent group transaction. Validation,
application and restoration use that same target. Other PIDs' parameters and
retained controller states must not change.

Validation and Apply must refer to the same target and mapping. Changing either
invalidates application eligibility and requires validation for the new
selection. A missing or incompatible mapping leaves Apply unavailable.

Apply the complete reviewed parameter set with the corresponding coherent
controller-state update. Use the existing initialization and transfer rules
to avoid an unintended output jump; do not write individual gains at unrelated
times or treat gain writes alone as state initialization. Unsupported mapping
or a changed controller revision must reject application without partial writes.

Tune and Validate only prepare and check the candidate. The selected running
controller changes only after the user presses **Apply** and the runtime
accepts that operation.

While awaiting runtime confirmation, disable the action and show **Applying…**
in the button. After confirmed adoption, show one short **Applied** message and
replace the button with **Restore previous settings**. If application fails,
show its specific reason in the same area and do not claim success. Use the
existing recoverable transaction contract to prevent duplicate writes.

## Restore and restart

Retain the exact confirmed pre-Apply parameter revision for the selected target.
**Restore previous settings** restores that parameter set using the existing
guarded rollback and coherent transfer behavior. Initialize any required live
state from the current observations; do not blindly replay old integral or
filter history after the process has moved. For a group, restore the complete
selected group coherently.

Disable the button while restoring and show **Restoring…**. Report **Restored**
only after runtime confirmation. If the active revision or target changed,
explain why restoration is unavailable instead of overwriting another change.
Apply and Restore never appear as competing primary actions. A new candidate
must pass validation before this action can offer Apply for that candidate.

Autosave preserves the study and confirmed application history without adding
Save/Open controls here. Apply writes active runtime parameters; it does not
rewrite the ST program or silently change startup/retain settings. After a
runtime restart, inspect actual values and follow the shared restart rules.
An old application receipt is not evidence that its values remain active.
Reopening must never automatically apply saved gains, replay controller state
or repeat an unacknowledged write.

## Layout

Example after successful validation:

```text
 Identify                 Tune                 Validate
                                               ━━━━━━━━

 [ Validate controller ]


 Requirement           Measured       Limit       Result
 Settling time          4.2 s          ≤ 5 s       Pass
 Overshoot              3 %            ≤ 5 %       Pass
 Steady-state error     0.1 °C         ≤ 0.2 °C    Pass


 Measured response                   ── Tuned  ╌╌ Current
 ┌─────────────────────────────────────────────────────┐
 │                         ╌╌╌╌                        │
 │                     ╌╌╌      ╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌   │
 │                  ────────────────────────────────   │
 │              ────                                   │
 │          ────                                       │
 │ ─────────                                           │
 │                                                     │
 └─────────────────────────────────────────────────────┘
                         Time (s)

 [ Apply ]
```

There is **no bottom status strip**: no Simulation, Live, Running, runtime
identity, scan counters, connection badges or separate SP/PV/MV value strip.
Do not add recording-management buttons, export buttons, revision bookkeeping,
Help/Details panels, extra summary cards or a plot-action toolbar to this
agreed layout.
