# Rust-first cell

Build and test a press cell whose whole program is Rust: `trust.toml` is its configuration, a
sequence runs the cell step by step, and machine tests check it against a simulated clamp and press.
You learn how a Rust-first project is laid out, and how `cargo test` tests the machine, not only the
code.

## What you learn

- A Rust-first project is a Cargo crate with `trust.toml` and no Structured Text of your own.
  `trust.toml` declares the resource, its task, the program instance and the bindings of the
  program's variables to I/O addresses, and truST writes the configuration from it.
- A sequence is straight-line Rust that waits: `s.until(..)` for a sensor, `s.wait(..)` for a time,
  and `.within(..)` for a move that must not take longer than its limit.
- Machine tests in the crate's own `tests/` run the program and its simulated clamp and press under
  `cargo test`, on a clock that only the test moves, so they give the same result on every run.

## What you need

- truST in VS Code, which brings `trust-runtime` and the toolchain that builds the Rust. No
  hardware: `simulation.toml` simulates the clamp and the press.
- Rust from [rustup](https://rustup.rs) with `cargo`, for the machine tests, and a clone of the truST
  repository. The SDK crates `trust-plc` and `trust-sim` are not on crates.io yet, and in the
  repository `cargo test` takes them from the repository itself. The tests run the `trust-runtime`
  that the environment variable `TRUST_RUNTIME` names, else the one on your `PATH`, else your truST
  extension's; it must be of the clone's version.
- About 20 minutes.

## Step by step

1. Open the folder `examples/rust_first_cell` of your clone in VS Code. Without a clone, choose
   **Start from example** in the truST side panel, then **Rust-first press cell**, and pick a folder
   under **Select destination folder**: VS Code opens the copy on `src/lib.rs`. Steps 2 to 4 work in
   the copy, and the machine tests of steps 5 and 6 once `trust-plc` and `trust-sim` are on
   crates.io (What you need). The project is a Cargo crate: `Cargo.toml` and `src/lib.rs` lie beside
   `trust.toml`, `runtime.toml`, `io.toml` and `simulation.toml`, and the machine tests are in
   `tests/cell.rs`.
2. Open `trust.toml`. It declares what a `CONFIGURATION` declares: the resource `CellRes`, the task
   `CellTask` every 10 ms, the program instance `Cell` of the Rust program `PRESS_CELL` on that
   task, and the bindings of `Cell`'s inputs and outputs to the fixture's addresses, from
   `"Cell.start" = "%IX0.0"` to `"Cell.ready" = "%QX0.2"`. Then open
   `src/generated/trust/configuration.st`: truST wrote it from `trust.toml`, and the build runs it.

    ```st
    (* GENERATED by trust-runtime from trust.toml - do not edit *)
    CONFIGURATION CellRes
    RESOURCE CellRes ON PLC
        TASK CellTask (INTERVAL := T#10ms, PRIORITY := 1);
        PROGRAM Cell WITH CellTask : PRESS_CELL;
    END_RESOURCE
    VAR_CONFIG
        Cell.start AT %IX0.0 : BOOL;
        Cell.part_present AT %IX0.1 : BOOL;
        Cell.clamp_closed AT %IX0.2 : BOOL;
        Cell.press_down AT %IX0.3 : BOOL;
        Cell.clamp AT %QX0.0 : BOOL;
        Cell.press AT %QX0.1 : BOOL;
        Cell.ready AT %QX0.2 : BOOL;
    END_VAR
    END_CONFIGURATION
    ```

3. Open `src/lib.rs`. `PressCell` declares the cell's inputs and outputs, and its sequence `run`
   is the cell's steps in order: `READY` waits for a part and Start; `CLAMP` closes the clamp and
   waits for its sensor, at most 1 s; `PRESS` lowers the press and waits for its sensor, at most
   2 s; `HOLD` holds the parts together for 500 ms; `LIFT` raises the press, at most 2 s;
   `UNCLAMP` opens the clamp, at most 1 s, and counts the part; `UNLOAD` waits until the part is
   taken out. When you save `src/lib.rs` or `trust.toml`, truST writes `src/generated/trust/`
   again.
4. In a terminal in the folder, build the project as the extension's Start builds it. The first
   build needs the truST toolchain: if `build` says that it is not installed, run
   `trust-runtime toolchain install` once.

    ```text
    trust-runtime build --project .
    ```

    It builds the Rust program into the program's image and prints what it wrote, here on an x86-64
    Linux computer, whose sizes differ a little from another computer's:

    ```text
    Wrote ./program.tpi
    Debug image 6212 bytes: code 2754, read-only data 28, starting memory 56
    Memory figure: 6251 bytes (areas 58, stack 5710, bookkeeping 475, retain capture 8)
    Sources: 2 file(s)
    ```

    The two sources are the files of `src/generated/trust/`: the configuration and the Rust
    program's declarations, `rust_pous.st`. It also names the install file for
    `trust-runtime ctl install` and the key that signed the image.

5. Run the machine tests:

    ```text
    cargo test
    ```

    The tests build the project once, with `trust-runtime build`, and each starts a simulator of
    its own. The four run in parallel, so their order changes from run to run:

    ```text
    running 4 tests
    test start_without_a_part_leaves_the_cell_ready ... ok
    test a_clamp_that_does_not_close_faults_the_cell_before_the_press_moves ... ok
    test a_press_that_does_not_come_down_faults_the_cell_at_its_limit ... ok
    test a_part_is_clamped_pressed_held_lifted_and_unclamped_in_turn ... ok

    test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 1.15s
    ```

    The first test runs 3 s of the cell's time, a whole part from Start to `UNLOAD`, in a fraction of
    that.

6. Read a failure. In `src/lib.rs`, set `PRESS_TIME_MS` to `500` and run `cargo test` again. Two
   tests fail:

    ```text
    ---- a_press_that_does_not_come_down_faults_the_cell_at_its_limit stdout ----
    assertion `left == right` failed
      left: 820
     right: 2320

    ---- a_part_is_clamped_pressed_held_lifted_and_unclamped_in_turn stdout ----
    Error: the cycle at 820ms faulted: Rust fault 3 (500, 510)
    ```

    The press needs 800 ms to come down, longer than the new limit: `PRESS`'s wait, the sequence's
    third, ran out after 510 ms, at 820 ms, though the press's sensor works. Put `2_000` back.

## What happened

**The configuration.** A Rust-first project's `trust.toml` is its `CONFIGURATION` (IEC 61131-3
§6.8) in TOML. truST writes `src/generated/trust/configuration.st` from it, with the declarations of
the Rust program in `rust_pous.st` beside it, and the build refuses a project whose generated files
are out of date, so the configuration that runs is always the one that `trust.toml` says. Each
binding is a `VAR_CONFIG` entry: the program declares `start` as an input, and the configuration
puts it at `%IX0.0`.

**The steps.** A wait of the sequence completes at the first later cycle at whose start its
condition holds, never at the cycle that began it. In words: a step that opens a valve at a cycle
goes on at the first cycle that sees the valve's sensor. Each sensor here follows its valve after
the cylinder's time `d`, 300 ms for the clamp and 800 ms for the press, so

> t_next = t_valve + d

where `t_valve` is the time of the cycle that opened or closed the valve, and `t_next` the time of
the cycle that enters the next step; every time here falls on a 10 ms cycle, so no rounding is
needed. `HOLD` ends at the first cycle at or after `t_hold + 500 ms`. Worked with the run's times,
from the cycle at 10 ms, the first that sees the part and Start:

| Step | Begins at | Because |
|---|---|---|
| `CLAMP` | 10 ms | the part and Start, written after the cycle at 0 ms |
| `PRESS` | 310 ms | 10 + 300: the clamp's sensor |
| `HOLD` | 1,110 ms | 310 + 800: the press's sensor |
| `LIFT` | 1,610 ms | 1,110 + 500: the hold |
| `UNCLAMP` | 2,410 ms | 1,610 + 800: the press's sensor clears |
| `UNLOAD` | 2,710 ms | 2,410 + 300: the clamp's sensor clears; `parts` is 1 |

One part takes 2.7 s from Start to `UNLOAD`.

**The limits.** `.within(t)` faults the program at the first cycle more than `t` after its wait
began; a wait of exactly `t` is still in time. With a cycle of 10 ms:

> t_fault = t_wait + t + 10 ms

where `t_wait` is the time of the cycle that began the wait. The fault names the wait point, its
place among the sequence's waits from 1, then `t` and the time waited, in milliseconds. Worked:
`PRESS`'s wait is the sequence's third and begins at 310 ms. With its limit of 2,000 ms and a press
sensor that never comes, the cycle at 310 + 2,000 + 10 = 2,320 ms faults, after a wait of 2,010 ms:
`Rust fault 3 (2000, 2010)`, as the test `a_press_that_does_not_come_down_faults_the_cell_at_its_limit`
checks. With the limit of 500 ms of step 6 the press, which needs 800 ms, comes too late for every
part: 310 + 500 + 10 = 820 ms and `Rust fault 3 (500, 510)`.

**The fault.** `runtime.toml` sets `policy = "safe_halt"`: a fault halts the resource and drives
the safe state of `io.toml`, which closes the press's valve so that the press lifts, and turns the
Ready lamp off; the clamp keeps the part. The program's variables keep their values for a look at
the fault: `Cell.active_step` still reads `PRESS`.

**The machine tests.** `trust_sim::Project::open(".")` opens the crate's own folder, which is the
project, and builds it with `trust-runtime build` once for all its tests. Each test then starts a
simulator of its own, a `trust-runtime` process that runs the program and `simulation.toml` on
logical time: `run_cycles` and `run_for` move it, so the 2.7 s of a part take only the time their
270 scans take. `write` sets an input as Live Values does, and `force` holds a sensor against the
simulation, as a broken wire would.

## Try it yourself

- Make the press slower: in `simulation.toml`, set the press's `delay_ms` to `2500`. The first test
  fails at the press's limit: its sensor would come at 310 + 2,500 = 2,810 ms, later than 2,310 ms,
  so the cycle at 2,320 ms faults with `Rust fault 3 (2000, 2010)`.
- Hold the parts for 1 s: set `HOLD_TIME_MS` to `1_000`. Every step from `LIFT` on comes 500 ms
  later, `LIFT` at 2,110 ms and `UNLOAD` at 3,210 ms: change the first test's expected times, and
  its 3,000 ms to 3,500 ms, until it passes.
- Count only what the operator takes out: move `self.parts = self.parts.wrapping_add(1);` after the
  `UNLOAD` wait. The first test fails, as `parts` is still 0 at 2,710 ms, and passes again when it
  reads `parts` after taking the part out.

## Reference

| File | What it holds |
|---|---|
| `Cargo.toml` | the crate, with `trust-plc` at this release's version and `trust-sim` for the tests |
| `src/lib.rs` | the program `PRESS_CELL` and its sequence |
| `trust.toml` | the configuration: resource, task, program instance and bindings |
| `src/generated/trust/` | the Structured Text that truST writes from `src/lib.rs` and `trust.toml`; commit it |
| `runtime.toml` | the runtime's settings: a cycle every 10 ms, and `safe_halt` on a fault |
| `io.toml` | simulated I/O and the safe state of a fault |
| `simulation.toml` | the clamp and the press: each sensor follows its valve |
| `tests/cell.rs` | the machine tests |

| Variable | Address | What it is |
|---|---|---|
| `Cell.start` | `%IX0.0` | the operator's Start button |
| `Cell.part_present` | `%IX0.1` | the fixture's part sensor |
| `Cell.clamp_closed` | `%IX0.2` | the clamp's sensor: closed |
| `Cell.press_down` | `%IX0.3` | the press's sensor: down |
| `Cell.clamp` | `%QX0.0` | the clamp's valve |
| `Cell.press` | `%QX0.1` | the press's valve |
| `Cell.ready` | `%QX0.2` | the Ready lamp |
| `Cell.active_step` | none | the step the sequence is in |
| `Cell.parts` | none | the parts pressed since the program started |

To run the cell on a machine, set `io.toml`'s driver to your I/O (Devices & Connections writes it),
move the bindings in `trust.toml` to your addresses, and set the three times in `src/lib.rs` from
your cylinders: each limit a little longer than the move takes on the machine.
