# Control engineering course

This course teaches control theory by applying it to real industrial equipment in 84 ordered, independently runnable truST projects. Each lesson explains the physical problem and required theory before the learner predicts, implements, experiments, compares, validates, and explains the result.

Use the lessons in numerical order unless you already meet a lesson's stated prerequisites. The practical stages listed below are the Control Studio stages used by that lesson; a lesson uses only the stages that its engineering question requires.

## Learner modules

The folders represent only the learning sequence. Each module answers the
problems exposed by the preceding module before introducing another class of
control problem.

| Module | Lessons | Learning progression |
| --- | ---: | --- |
| [01 · Feedback foundations and temperature control](./01-feedback-foundations-and-temperature-control/) | 01–18 | Start with loop anatomy and ON/OFF control, build P and PI carefully, confront implementation limits, then derive, identify, validate, and tune the first plant model. |
| [02 · Derivative action and dynamic response](./02-derivative-action-and-dynamic-response/) | 19–25 | Use visible mechanical oscillation to learn P, PD, PID, damping, derivative kick, filtering, nonidealities, sampling, and digital realization as transferable concepts. |
| [03 · Production-quality digital PID](./03-production-quality-digital-pid/) | 26–30 | Turn the earlier equations into a reusable controller with correct forms, initialization, modes, bumpless transfer, atomic updates, and fail-closed data handling. |
| [04 · Controller selection and plant models](./04-controller-selection-and-plant-models/) | 31–36 | Select the simplest controller from requirements, then learn why self-regulating, integrating, delayed, oscillating, inverse-response, nonlinear, and coupled plants need different models. |
| [05 · Experiments, identification, and validation](./05-experiments-identification-and-validation/) | 37–41 | Design safe informative experiments, reject poor data, compare model structures, and validate a frozen model on evidence not used for fitting. |
| [06 · PID tuning methods](./06-pid-tuning-methods/) | 42–44 | Compare staged manual tuning, relay-derived tuning, and model-based tuning without treating any formula as universally best. |
| [07 · Classical stability and frequency design](./07-classical-stability-and-frequency-design/) | 45–50 | Progress from algebraic stability to root locus, Bode, Nyquist, sensitivity, loop shaping, and discrete-time stability. |
| [08 · Tuning qualification and automation](./08-tuning-qualification-and-automation/) | 51–52 | Compare eligible tuning methods against common evidence and audit the complete automatic Test–Identify–Tune–Validate sequence. |
| [09 · Industrial control structures](./09-industrial-control-structures/) | 53–60 | Add feedforward, cascade, ratio, split-range, override, gain scheduling, delay compensation, and valve diagnosis only when a measured failure justifies them. |
| [10 · Multivariable control](./10-multivariable-control/) | 61–63 | Measure interaction, calculate RGA, qualify decoupling, and decide when decentralized loops are no longer sufficient. |
| [11 · State-space, estimation, and predictive control](./11-state-space-estimation-and-predictive-control/) | 64–68 | Test controllability and observability before designing observers, Kalman filters, LQR/LQG, and constrained MPC. |
| [12 · Nonlinear, adaptive, and robust control](./12-nonlinear-adaptive-and-robust-control/) | 69–72 | State local validity honestly, compare nonlinear cancellation and scheduling, supervise adaptation, and qualify robustness against declared uncertainty. |
| [13 · Networked, fault-aware, and diagnostic control](./13-networked-fault-aware-and-diagnostic-control/) | 73–75 | Preserve safe authority through communication faults, isolate supported failures, degrade deliberately, recover explicitly, and diagnose before retuning. |
| [14 · Integrated capstones](./14-integrated-capstones/) | 76–84 | Combine requirements, modelling, experiments, controller design, abnormal validation, evidence, approval, rollback, and lifecycle decisions on complete systems. |

## For control engineers

The lesson folders intentionally follow the learner's sequence rather than an
overlapping technical taxonomy. Use the following indexes when you already
know the technique, plant behavior, or engineering task you need. A linked
lesson explains the prerequisites, validity limits, experiment, implementation,
and evidence needed to decide whether the technique is appropriate; it is not
merely a code sample.

## Project and evidence boundary

Every numbered lesson directory is a complete truST project using ordinary
controller-facing I/O and the shipped simulator and Control library. The
experiments produce Simulation evidence; they do not claim physical-plant
commissioning. A physical experiment or controller application still requires
the independent safety review and immediate explicit approval described by
Control Studio.

Stable lesson identities and paths are declared once in `../catalog.json`.
Each project's `lesson.json` owns its equipment, objective, technique,
workflow, safety limits, prerequisites, and evidence contract. Specification
38 owns the 84-lesson progression, and
`docs/public/examples/learning-paths.md` presents the same progression in the
public documentation.

Do not put project configuration or alternate controller implementations in a
module directory. Shared product behavior belongs in the truST Control library,
while each lesson carries only the packaged library source required to remain
runnable after the gallery copies it outside the repository.
